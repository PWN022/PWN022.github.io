# 门店接口未授权泄露门店负责人真实姓名与手机号（脱敏版）

> 脱敏说明：真实域名已替换为 `*.example.com`，真实姓名、手机号、门店名、详细地址、经纬度、内部 ID 已打码；接口路径与参数名保留用于复现与修复。

- 漏洞编号：`finding #REDACTED`
    
- 严重级别：中危
    
- 漏洞类型：未授权访问 / 敏感信息泄露（Unauthenticated Sensitive Information Disclosure）
    
- 影响资产：`https://api.example.com/api/Store/GetStoreList`、`/api/Store/GetStoreById`、`/api/Store/GetDefaultStore`（`endpoint #REDACTED`，CoreShop 商城 API 端，ASP.NET Core / IIS）

## 一、文字说明

`api.example.com` 的 `StoreController` 中读取门店信息的三个动作（`GetDefaultStore`、`GetStoreList`、`GetStoreById`）**未配置鉴权**：既无类级 `[Authorize]`，也无动作级 `[Authorize]`。匿名访问者无需任何 token / 认证头，仅用空 JSON 体 POST 即可获取全部门店记录，其中直接包含门店负责人的**真实姓名（linkMan）与手机号（mobile）**，以及门店详细地址、经纬度坐标等字段。

实测匿名可取到全部 2 条门店记录（以下为脱敏展示）：

- 门店A — 负责人A / `1XX****XXXX` / 某市某区某地址A
    
- 门店B — 负责人B / `1XX****XXXX` / 某市某区某地址B

诚实边界：

- **已确认**：上述三个接口匿名 POST 返回 HTTP 200 及门店实体，包含 `linkMan`、`mobile`、`address`、`coordinate` 等字段。
    
- **已确认**：同一控制器内带 `[Authorize]` 的动作匿名访问被拒，返回 `code:14007`，说明鉴权机制存在但未覆盖上述三个接口。
    
- **未证实/限制**：当前实例仅 2 条门店记录，未验证大规模批量拉取；未发现管理员凭据或可用于进一步入侵的信息；同批次排查的 `/api/Payments/GetList`、`/api/Store/GetRecommendKeys` 匿名返回参数/关键词，但未包含个人敏感数据，不并入本报告。
    
- 全程只读，未上传/篡改/删除任何文件，未进行批量操作。

## 二、影响与危害

- 泄露的是**可直接识别自然人身份的个人信息（PII）**：真实姓名 + 手机号，结合门店地址/坐标可精确定位到人，可被用于电信诈骗、精准社工、骚扰营销，属于《个人信息保护法》意义上的个人信息泄露。
    
- 信息面向任何匿名访问者开放，无需注册、无需交互，攻击者可脚本化获取；接口支持分页参数，当前环境仅 2 家门店，但泄露字段本身敏感性高，且可结合地址/坐标定位到具体自然人。
    
- **为何定为中危**：三个接口完全免鉴权，匿名即可直接获取门店负责人真实姓名与手机号，属于可直接识别自然人的 PII 泄露；利用无需任何凭据、可脚本化复现，结合地址与经纬度可进一步定位到人。虽当前实例门店数量仅 2 家、未达到“大量个人信息泄露”的高危规模，且不同于可直接接管账号或 SQL 注入类漏洞，但 PII 敏感性与免鉴权直接暴露使其风险高于一般信息泄露，故按中危判级。
    
- 未发现该接口泄露管理员凭据或可用于进一步入侵的信息，故未进一步升级等级。备注：同批次排查还发现 `/api/Payments/GetList` 匿名返回支付方式参数、`/api/Store/GetRecommendKeys` 匿名返回推荐关键词，但**均未包含个人敏感数据**，不并入本报告。

## 三、相关 URL

|    用途     |                                        URL                                        |
| :-------: | :-------------------------------------------------------------------------------: |
|  门店列表接口   |        `https://api.example.com/api/Store/GetStoreList`（POST，空 JSON `{}`）         |
| 按 ID 读取门店 | `https://api.example.com/api/Store/GetStoreById`（POST，JSON `{"id":"<STORE_ID>"}`） |
|  默认门店接口   |       `https://api.example.com/api/Store/GetDefaultStore`（POST，空 JSON `{}`）       |
|  对照鉴权接口   |     `https://api.example.com/api/Store/GetStoreByUserId`（匿名访问返回 `code:14007`）     |

`id` 取自上一步列表返回；报告中以 `<STORE_ID>` 代替内部编号。

## 四、涉及账号密码

**无。** 上述三个接口免鉴权，利用无需任何账号、密码或令牌。同控制器内带 `[Authorize]` 的动作匿名访问会返回 `code:14007`，可作对照组。

## 五、利用过程（复现步骤）

1. 匿名拉取门店列表：

```
curl -sk -X POST https://api.example.com/api/Store/GetStoreList \
  -H 'Content-Type: application/json' -d '{}'
```

→ HTTP 200，`totalCount=2`，`data[].linkMan`、`data[].mobile` 返回明文 PII（报告中已打码）。

2. 匿名按 ID 读取单个门店（id 取自上一步返回）：

```
curl -sk -X POST https://api.example.com/api/Store/GetStoreById \
  -H 'Content-Type: application/json' -d '{"id":"<STORE_ID_1>"}'
curl -sk -X POST https://api.example.com/api/Store/GetStoreById \
  -H 'Content-Type: application/json' -d '{"id":"<STORE_ID_2>"}'
```

→ HTTP 200，返回单个门店完整实体，含 `linkMan`、`mobile`、`address`、`coordinate`。

3. 匿名读取默认门店：

```
curl -sk -X POST https://api.example.com/api/Store/GetDefaultStore \
  -H 'Content-Type: application/json' -d '{}'
```

→ HTTP 200，返回默认门店完整实体，含同类 PII。

4. 对照组：同一控制器下带 `[Authorize]` 的动作匿名访问被拒：

```
POST /api/Store/GetStoreByUserId {"userId":1}
-> {"status":false,"msg":"很抱歉，授权失效，请重新登录!","data":14007,"code":14007}
```

上述步骤均在**不带任何 `Authorization`/token 头**的情况下返回 HTTP 200 及真实门店 PII，即证明未授权访问成立。全程只读，未改动任何数据。

## 七、修复建议

1. **补齐鉴权/收紧访问控制（首选）**：为 `GetStoreList`、`GetStoreById`、`GetDefaultStore` 增加 `[Authorize]`，或在 `StoreController` 上加类级 `[Authorize]`，并对确需匿名开放的展示动作单独标 `[AllowAnonymous]`，形成“默认拒绝”的白名单模型；全局注册鉴权回退策略，避免逐动作手写 `[Authorize]` 的遗漏风险。
    
2. **后端字段裁剪/输出脱敏（必须）**：为对外接口定义专用 ViewModel/DTO，只返回门店名、展示地址等必要字段，**剔除 `linkMan`、`mobile` 等个人敏感字段**；确需展示时以掩码形式返回（如 `1XX****XXXX`）。切勿直接返回 `CoreCmsStore` 数据库实体。
    
3. **数据最小化与审计**：核查其余未授权接口是否同样返回 PII，统一按最小必要原则收敛；对门店/用户等含个人信息的资源建立字段级访问规范。
    
4. **监控与加固**：对该接口增加访问频率限制与异常批量拉取告警；结合 WAF/网关对敏感接口做未授权访问拦截。
    
5. **回归验证**：修复后匿名请求上述三接口应返回 `code:14007`（授权失效）或脱敏数据；携带合法门店/管理端 token 方可返回完整内部字段。以“匿名请求是否仍返回明文手机号”作为核验标准。
